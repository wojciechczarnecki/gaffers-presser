# Design decisions

Binding architectural and process decisions. Append rows at the end (append-only) — then
parallel lanes merge trivially. Record a decision in the same PR in which it takes effect.
A row added by a PR that is not merged yet is edited in place when that PR changes its mind;
once a row is on `main`, a change is a new row that names the one it supersedes.

| 2026-09-27 | Code is organised by business module (`app/fpl`, later `app/leaks`, `app/presser`…), each holding its own tables, payload schemas and jobs; a file that outgrows one subdomain becomes a package split by subdomain (e.g. `app/fpl/models/` with `reference`, `leagues`, `snapshots`) that re-exports its names | global `models/`, `schemas/`, `services/` layers; one file per class | a feature lives in one directory and parallel lanes rarely touch the same files; subdomain files keep related tables together without a file per class |
| 2026-09-27 | The worker's schedule is derived from the gameweek calendar and a job run log table: reference sync every 60 min (every 15 min in the 48 h before a deadline, every 24 h with no future deadline), deadline snapshots at T-30 and T-5, results sync then league sync once a gameweek is `finished` + `data_checked`, and a catch-up of missed results and league syncs on start; one worker holds the schedule at a time | a fixed cron-like table; a league sync right after each deadline; state derived from the collected data | restarts and downtime heal themselves; the flag timeline is dense where flags move; every consumer needs final league data; the run log is the input for failure alerting (spec 002) |
| 2026-09-27 | Deployment: a Docker image of `backend/` on Railway, auto-deployed from `main` after green CI; `alembic upgrade head` runs as the Railway pre-deploy command; production PostgreSQL runs from `pgvector/pgvector:pg16` with a volume | manual `railway up`; migrations run by hand; the Railway Postgres template | merging a PR is the deploy and new code never runs on an old schema; the same database image as Compose and the tests, with pgvector ready for Stage 2 (spec 002) |
| 2026-09-28 | Single worker and job serialisation through PostgreSQL advisory locks — a session lock held by the worker for its whole life, a transaction lock taken around every job in both the worker and the FPL CLI | a lock table with heartbeats; relying on Railway running a single replica | released by PostgreSQL itself when a process dies, no new table, and it covers the old and new deployment overlapping during a Railway restart (spec 002) |
| 2026-09-28 | The 60 s p95 latency target covers detection only (post on X → first fetch by our system); LLM extraction and e-mail delivery come on top | 60 s from post to the owner's inbox | the source and the polling strategy are what the target holds accountable; the other legs are measured in their own stages (spec 003) |
| 2026-09-28 | Tweet ingest polls one public X List (ID in configuration) in its own loop inside the worker process — every 20 s in the 90 min before a deadline, every 30 min otherwise — independent of the FPL job queue; a source's retry-after delays the next poll by at most 30 min | a digest of one or two polls before the deadline; per-account polling; the shared FPL job queue; a separate process | only continuous polling in the window meets 60 s at negligible cost; one request per poll for all accounts; FPL jobs never delay a leak while staying one process and one Railway service (spec 003) |
| 2026-09-28 | Three `TweetSource` adapters — twscrape (the library) for the free scraper, and plain `httpx` (no extra client library) for both twitterapi.io and the official X API v2; posts are keyed by X ID with `INSERT … ON CONFLICT DO NOTHING` so the first fetch always wins; the last seen ID for polling is `max(tweet.x_id)` and only ends paging — every post on the fetched pages is stored, so a post that becomes visible after a newer one is kept; a post that fails to map is skipped and logged by error class, not the whole page; twscrape's telemetry is switched off (`TWS_TELEMETRY=0`) | tweepy or `xdk` for the official API; an upsert that would overwrite `first_fetched_at`; a separately tracked last-seen-ID column; dropping posts at or below the last seen ID | one GET endpoint each needs no client library and reuses the pinned `httpx`/`MockTransport` pattern; the insert-or-ignore gives exact once-per-post storage for free; the stored posts are already the source of truth for the last seen ID (spec 003) |
| 2026-09-28 | twscrape is the tweet source we configure (`TWEET_SOURCE=twscrape`, recommended in `.env.example` and DEPLOYMENT; an empty value still disables the ingest); measured p95 detection latency 25.9 s on 20 controlled posts — [ADR 0005](adr/0005-default-tweet-source-twscrape.md) | twitterapi.io; the official X API | the only candidate measured in full, within the 60 s target at 0 PLN; twitterapi.io ran out of free credits during the run (spec 003) |
| 2026-09-28 | Extraction is a LangGraph flow of two stages: the LLM names players as written with event type (out / doubt / benched / confirmed starter) and certainty (confirmed / likely / rumour); a deterministic lookup over the current season's players with aliases and team context links them, and the LLM only chooses among candidates when the lookup is ambiguous | the whole player list in every prompt; an agent calling a player-search tool; a 0–1 certainty score | ~7k tokens per post for the full list; a tool loop adds calls and latency; the lookup is cheap, explainable and evaluated on its own; a small defined scale labels consistently (spec 004) |
| 2026-09-28 | Relevance rule: availability events (out, doubt) count whatever the competition; line-up events (benched, confirmed starter) only for the next Premier League match; national-team, cup, European and women's line-ups give no events; reposts are extracted like ordinary posts and attributed to the list account | Premier League events only; everything plus a competition field; skipping reposts | an injury on international duty changes FPL availability, a national-team line-up does not; FR-1.3 stays four event types; `is_repost` stays on the post for Stage 2 corroboration (spec 004) |
| 2026-09-29 | The event type describes the player's next Premier League match: an injury that takes a player out of a national-team, cup or European match, or out of the camp, is `doubt` unless the post says he misses the next PL match (`out`); a post saying the knock is not serious or that he should be available gives no event; certainty stays the strength of the source. Extraction prompt v2 and evaluation set v1 are labelled this way | `out` for any match the player misses; a competition field | an `out` alert must mean "will not play in FPL" — most international-break withdrawals are fit for the next gameweek; FR-1.3 stays four event types (spec 005 precondition, the owner's review) |
| 2026-09-28 | Extraction runs in its own loop in the worker process, independent of the tweet poller and the FPL jobs, plus a re-extraction CLI; every extraction is kept, the latest successful one is current | a CLI only until Stage 2; overwriting the previous extraction | a slow or failing LLM never delays tweet polls; extraction latency is measured in production from day one; history allows comparing models and prompts (spec 004) |
| 2026-09-28 | LLM tracing on Langfuse Cloud (EU region, free plan) | self-hosted Langfuse on Railway; local-only Langfuse | self-hosted Langfuse v3 needs ClickHouse, Redis and object storage; the volume fits the free plan; production stays traced (spec 004) |
| 2026-09-28 | The extraction evaluation set lives in the repository as JSONL with the full text of public posts, split dev / test (prompt work on dev only), pre-labelled by a model and reviewed case by case by the owner; a model passes with event F1 ≥ 0.85, linking accuracy ≥ 0.95, false-alarm rate ≤ 5% and a projected cost ≤ 5 PLN a month on a run with no errored case (an errored case never counts as a correct negative), and the cheapest passing model is the default | X IDs only with texts hydrated locally; synthetic paraphrases only; no split; no thresholds | a reproducible evaluation anyone can rerun; public news posts are not private users' data (the X terms-of-service risk is accepted by the owner); an untouched test split keeps the comparison honest (spec 004) |
| 2026-09-29 | OpenRouter is the only LLM provider, through `langchain-openrouter` (`ChatOpenRouter`, exact pin); `OPENROUTER_API_KEY` is the switch for extraction, `LLM_MODEL` and `LLM_FALLBACK_MODEL` are optional, `LLM_PROVIDER` and `--provider` are removed; the fallback goes through OpenRouter's `models` list; an outage of OpenRouter itself is an accepted risk — [ADR 0006](adr/0006-default-extraction-model-openrouter.md) | keeping `langchain-openai` with a `base_url`; direct Google / OpenAI / Anthropic adapters; a client-side `with_fallbacks` | one key reaches every candidate and the first-party client handles structured output, reasoning and routing natively (spec 005) |
| 2026-09-29 | The default extraction model is `openai/gpt-6-luna` (the only candidate passing every threshold, 0.49 PLN a month) and the fallback is `google/gemini-3.1-flash-lite`; a fallback must be pair-compatible with the default (same structured-output method and reasoning effort), so the rule's best other candidate `qwen/qwen3.8-flash` was skipped — [ADR 0006](adr/0006-default-extraction-model-openrouter.md) | `qwen/qwen3.8-flash` (higher F1, cannot answer the primary's request); `z-ai/glm-5.3-flash` (same) | measured on the reviewed test split with the frozen prompt (spec 005) |
| 2026-09-29 | Request settings per model live in the committed `backend/app/extraction/model_settings.toml`: the lowest reasoning level each model allows, `temperature` only where the model lists it, an optional structured-output method, and `require_parameters` on every request; a model outside the file fails the worker on start | reading `/api/v1/models` at start; each model's default reasoning | evaluation and the worker send the same recorded setting, and it is reproducible without a network call (spec 005) |
| 2026-09-29 | Embeddings go through OpenRouter (the `openrouter` SDK pinned directly) behind an own `Embedder` interface; the default model is `openai/text-embedding-3-small`, overridable by `EMBEDDING_MODEL`; embeddings are keyed by (post, model) so several models live side by side; vector search is exact, with no ANN index | the OpenAI API directly; `langchain-openai` with a `base_url`; one vector column per post; HNSW now | one provider and one key (ADR 0006); model comparison and re-indexing without losing the current index; a few thousand posts a season need no ANN (spec 006) |
| 2026-09-29 | Every stored post is indexed (reposts and replies too, as filters); hybrid search fuses full-text (English configuration, `unaccent`; query lexemes are OR-ed, as prefix matches from 3 characters on, so `injured` finds `injury`) and vector rankings with RRF, `k = 60`, depth 50 per mode; a failed query embedding, or a model with no embeddings yet, degrades hybrid to full-text with the vector leg marked failed | only posts with extracted events; weighted score fusion | retrieval adds the posts extraction did not link; RRF needs no score calibration (ADR 0002) (spec 006) |
| 2026-09-29 | Posts are embedded in their own loop in the worker process, independent of the tweet poller, extraction and FPL jobs, plus an `index` CLI for re-indexing; never-attempted posts go before retries of failed ones, and a post is retried at most 15 times in total by the loop | CLI only; a step in the extraction loop | fresh posts are indexed within seconds before a deadline; an embedding outage never blocks extraction (spec 006) |
| 2026-09-29 | Code shared by AI features (OpenRouter and Langfuse settings, tracing, the price catalogue) lives in `app/llm/`; the clock lives in `app/core`; chat-specific settings and each feature's evaluation stay in their module | retrieval importing from `app.extraction`; a shared evaluation framework | retrieval is the second consumer, alerts and the presser follow; the evaluations differ in metrics (spec 006) |
| 2026-09-29 | The retrieval evaluation set lives in the repository: a frozen corpus snapshot of public posts plus ~40 queries (event-templated and LLM-written, ~10 in Polish) split dev / test, the corpus is loaded into its own schema `retrieval_eval` and never into the live `tweet` table; candidates pooled from the three modes, binary relevance pre-labelled by a model and reviewed by the owner; recall@5, recall@10 and MRR per mode with separate English and Polish slices | the owner writing every query; graded relevance with nDCG; evaluating against the live `tweet` table | realistic corroboration queries plus variety; the Polish slice checks cross-lingual retrieval before Stage 4; a frozen corpus keeps runs reproducible (spec 006) |
| 2026-09-30 | Corroboration lives in its own module `app/corroboration/` and is computed on demand for a player at a moment (`as_of`, `new_since`), over the window `[start, as_of)` where `start` is the latest deadline at or before `as_of` (the 7 days before `as_of` without one; `--since` overrides): the anchor is the player's newest current extraction event in the window, and every other post about him is labelled `supports` / `contradicts` / `related` against it — extracted claims by a fixed table (the same type supports; `confirmed_starter` against `out`/`doubt`/`benched` contradicts; any other pair of the three is related), retrieved posts with no event for the player by an LLM judge (the search's query embedding has a 5 s timeout, so a slow provider degrades it to full-text); independent accounts are original authors (a repost counts as its original author), each counted once by its newest labelled post; the result carries a reversal flag and a strength grade (`high` / `medium` / `low`, explicit thresholds on certainty and supporting accounts, lowered by fresh contradictions, with a hook for Stage 4 credibility) | a majority vote across accounts; one corroboration per new post; a worker loop with a stored table; the grade in the alert spec | a leak minutes before the deadline must override a week of earlier news; the alert schedule (T-2h digest, T-30/T-10 news, breaking) asks for the same player at several moments; the grade is an assessment of the evidence, reused by alerts and Q&A (spec 007) |
| 2026-09-30 | The corroboration judge is a narrow LLM step: it re-reads only the retrieved posts (at most 10 per corroboration) that carry no current event for the player and labels them against the anchor under the extraction relevance rule; its evaluation set lives in the repository as JSONL (anchor, player, post, label), split dev / test, pre-labelled by `anthropic/claude-haiku-4.5` (another vendor and a tier above the default judge `openai/gpt-6-luna`) and reviewed by the owner; each judge call is an explicit Langfuse generation under one trace per corroboration (our own tracer rather than the LangChain callback, because the cost comes from `prices.toml`) | SQL claims only with retrieval as uncounted context; improving extraction recall instead; the judge's own model pre-labelling | extraction reads each post blind and misses players in long posts; a question about one known player over a handful of posts recovers them; a model grading itself is circular (spec 007) |
| 2026-09-30 | Chat-model code shared by AI features lives in `app/llm/`: the OpenRouter chat-model factory, the model-settings catalogue (`model_settings.toml`), a structured call returning usage and cost, and one retry-with-back-off helper; the current extraction of a post has one public query in `app/extraction/store.py` (the only code besides `app.extraction` that may import it is `app/retrieval/evaluation/`, which reads events from it); deadline helpers live in `app/fpl/deadlines.py`; embedding calls take a per-call timeout. `app/llm/` holds `models.py` (the catalogue), `chat.py` (the factory and settings), `structured.py` and `retry.py`. Supersedes the 2026-09-29 row's "chat-specific settings stay in their module" and the path in the 2026-09-29 row on request settings per model (`backend/app/extraction/model_settings.toml` → `backend/app/llm/model_settings.toml`; the rest of that row stands) | a builder per feature; keeping `model_settings.toml` in `app/extraction` | the judge is the third chat consumer (after extraction and the retrieval evaluation), and alerts need deadlines next (spec 007) |
| 2026-09-30 | A refactor or shared abstraction that a feature needs is done in that feature's spec, not deferred to a cleanup | backlog entries for later refactors | many interdependent modules are built in quick succession; deferred duplication multiplies with every new consumer (the owner, spec 007) |
| 2026-09-30 | The original author of a repost is stored in `tweet.reposted_author_handle`, filled by every `TweetSource` adapter from its payload and backfilled from `raw`; extraction keeps attributing a repost to the list account | parsing `RT @handle:` from the text | explicit and independent of text formatting; independence counting needs the original author (spec 007) |
